# Member Overview — 20 October 2026

The member `/portal/member/dashboard` now uses a fixed authenticated bridge at
`GET /api/membership/overview`, backed by `GET /api/v1/membership/overview`.
The server derives the member from `Member.user_id == session.user_id`; no email,
member ID or user ID supplied by a caller selects records. Query selectors are
rejected by both bridge and backend. Canonical member role plus `members:own`,
`applications:own`, `fees:own` and `subscriptions:own` are required on every
overview request, with live permission denials and session expiry enforced.
Because Fees also returns subscriptions, it now requires both `fees:own` and
`subscriptions:own`; an explicit subscription denial cannot be bypassed there.

## Displayed records and boundaries

- Membership status comes from the existing approval/activation record linked to
  both the account/member and membership application. A legacy member/account link
  or joined date alone does not establish approval: it shows **Not confirmed**.
  An account without a linked member has a distinct empty state and office link.
- The registration payment, actual reference/date and verification status are
  shown. Legacy fee records without verification evidence remain identified as
  historical records; their recorded Paid status does not invent verification.
- Overview and Fees share the **same** backend fee/subscription reader. Existing
  verified application payments are read, never copied or posted again. Member
  ownership applies to every financial query.
- Savings-category snapshots are selected only through the owned membership
  application's member link. Original purpose, notice, version and date remain
  visible. Multiple historical snapshots are shown individually, never combined
  into a new choice. They are explicitly expressions of interest, not acceptance
  of terms or approved savings-plan enrolments.
- Formal plan approval/terms remain unconfigured. Legacy `member_plans.is_active`
  links are not treated as proof of approval and are not presented as approved
  enrolments. This is an explicit limitation, not a claim that legacy rows are absent.
- **Savings summary not available yet** is shown without any numerical balance,
  including zero. The existing helper mixes currencies and lacks the reconciled,
  immutable contribution/ledger guarantees required for a reliable total. No
  verified-status-only sum, fee/subscription amount or combined-currency figure
  is passed off as savings. Ledger/reconciliation work remains separate.
- Subscription start month comes from activation's persisted next-calendar-month
  snapshot, using the existing Africa/Harare calculation. Actual monthly records,
  currencies and Pending/Paid status are shown without generating new rows.
  The due day stays unset. Unapproved historical due-date/overdue classifications
  are not interpreted: the shared read model returns no due date, and unfamiliar
  statuses request office review. Original stored rows remain unchanged.
  Only the initial next-month subscription is generated by activation; automatic
  subsequent monthly generation remains future work.

## Interface and data preservation

The existing dark-and-green portal shell/navigation is retained, with responsive
status/fee/subscription cards and a separate interest panel. Loading, denied,
unlinked, empty, error and retry states contain no fixtures or invented totals.
Links go only to supported Fees and public Contact screens. Expired sessions use
the existing refresh/login handling. No registration, approval or payment action
is introduced on this read-only screen.

No schema migration is required, so no existing-database migration or new
backup/restore drill is necessary for this change. Tests use isolated synthetic
PostgreSQL and disposable browser services, never the office database.
